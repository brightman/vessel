# 项目文档生成与维护规则

> 版本：1.0 · 日期：2026-10-31 · 状态：本仓库已采用
>
> 适用：本仓库内由人和 AI Agent 协作开发的项目与后续任务。用户于 2026-10-31 要求写入 [仓库 AGENTS.md](../AGENTS.md)，本规则据此生效。其他项目可复用本文，采纳时确定自己的文档根目录。

## 1. 现状与结论

WiseLife 首轮索引收录 197 份已有文档与文字资料，其中 65 份位于 `superpowers` 目录：17 份设计、48 份实施计划。还有原型说明、验证记录、开发说明、许可证等。目录与文内引用说明项目广泛采用了 Superpowers 流程，但不能据此断言全部文档的生成来源。

Superpowers 的 `brainstorming` 默认产出带日期的设计，`writing-plans` 默认产出带日期的实施计划。这有利于记录一次任务的上下文，但项目还需要长期维护的产品和技术说明。

本次整理发现的主要问题：

- 同一产品的文件散落在仓库根目录和 App 目录，容易漏查。
- 设计、实施计划和验证记录缺少稳定的互相引用。
- 部分旧文档仍保留当时的“未实现”或“未验证”，阅读时容易误当作现在的状态。
- 同一规则散落在多份任务记录中，例如录音文件粒度、ASR 空白候选门槛和回顾刷新策略。
- 有些文档没有日期；有些只有文件名日期，却又追加了后续变更。

**核心规则：当前说明持续更新，任务过程按需记录，历史事实保留原貌，索引统一导航。**

## 2. 文档分为四类

| 类型 | 回答的问题 | 生成和修改方式 |
| --- | --- | --- |
| 当前说明 | 产品现在约定怎样工作？系统怎样实现？ | 每个主题有一个主要说明文件，使用稳定文件名；发生变化时直接修改相关章节 |
| 任务记录 | 这次为什么改、准备怎么改、实际做了什么？ | 按任务和日期建目录；设计、计划、验证按需要创建，避免每次都生成全套 |
| 决策记录 | 为什么选择这个方案？有哪些重要取舍？ | 只为重要决策建立 ADR；被新决策替代时保留原文并双向链接 |
| 导航与变更 | 去哪里找？什么时候发生了什么变化？ | 维护总索引、功能阅读路径和简短变更记录，链接到原文 |

“当前说明”指当前认可的产品与技术约定。计划功能必须标明未实现；实际交付状态由实施和验证证据说明。设计获批、代码完成、真机验证、发布上线是不同事件。

## 3. 推荐目录与呈现形式

```text
<project-root>/
├── README.md                    # 项目入口、运行方式、文档入口
├── AGENTS.md                    # Agent 执行规则与文档规则链接
├── docs/
│   ├── INDEX.md                 # 总索引：产品、技术、日期、模块、验证发布
│   ├── CHANGELOG.md             # 按日期的简短变更与关联任务
│   ├── documentation-rules.md   # 本项目采用的规则
│   ├── product/                # 当前产品与交互说明，按模块组织
│   ├── technical/              # 当前架构、数据、接口、处理流程
│   ├── decisions/              # 重要架构／产品决策 ADR
│   ├── work/
│   │   └── YYYY-MM-DD-topic/    # 一次任务，可包含 design/plan/verification
│   ├── releases/               # 发布版本、构建、部署与回滚记录
│   └── assets/                 # 文档必要的图示与脱敏证据
└── prototype/                  # 可运行的 HTML 产品原型
```

- 目录按实际内容创建，不预先生成空白模板或一批待填文件。
- 文本说明以 Markdown 为维护源；原型使用 HTML；流程图优先用 Mermaid。
- HTML 文档门户可从同一份 Markdown／元数据生成，不再维护另一套正文与目录。
- 一个独立项目确定一个文档根目录。Monorepo 中，App 专属文档归 App；跨项目规范放仓库根目录并链接引用。
- 已有项目沿用可用路径，通过索引建立关联；集中搬迁另作任务，保留旧入口或重定向说明。
- 文件名用稳定、可搜索的英文短名，正文标题可以用中文。避免 `final`、`new`、`最新版` 等不可判断的命名。

## 4. 什么情况下生成文档

| 变更类型 | 最小必要动作 | 何时增加文档 |
| --- | --- | --- |
| 文案、间距、局部样式 | 修改相关原型／现有说明；在 PR 或任务中记录检查结果 | 交互约定变化时更新产品说明 |
| 小型 Bug 修复 | 记录原因、修复和验证；更新受影响的现有规则 | 涉及数据丢失、恢复、重复事故时建立独立事故或验证记录 |
| 既有规则调整 | 更新主要说明、相关原型／技术章节，补充变更与边界验证 | 新的实现路径较复杂时增加实施计划 |
| 新功能、新流程 | 产品目标、范围与验收标准；涉及界面时提供原型；更新相关技术设计 | 跨模块或多步骤工作增加任务计划 |
| 数据库、协议、权限、数据生命周期调整 | 技术设计、兼容／迁移／恢复策略及验证范围 | 重要取舍建立 ADR；破坏性迁移记录回滚与用户影响 |
| 实验、模型评估 | 问题、输入范围、方法、结果、局限、是否采用 | 采用后把结论合入当前说明；实验本身保留 |
| 发布 | 版本、提交／构建标识、渠道、发布结果与回滚方式 | 设备／平台限制和未验证项明确列出 |

按风险和复杂度决定文档量。正常的小修复不需要机械生成“产品设计＋技术设计＋计划＋独立验收”四份文档。已有说明能够承载的内容直接更新。

## 5. 一次任务的文档流程

### 开始前

1. 读取项目 `AGENTS.md`、文档总索引和对应模块的当前说明。
2. 搜索是否已有同主题设计、计划或未完成任务，确定本次更新的主要文件。
3. 明确需求、约束、验收方式和已获得的授权；已有明确决定继续沿用。

### 设计与实现中

1. 新产品行为先写清目标、输入输出、关键状态、异常与验收标准；需要评审的 UI 先更新原型。
2. 产品说明描述用户可观察的行为；技术说明描述实现、数据、边界与恢复机制，互相引用。
3. 同一任务的计划在原文件更新进展；不要每次继续工作就另建一个日期文件。
4. 发生重要取舍时记录原因、备选方案、影响和决策来源。只有实际获得批准才能记录批准人和批准日期。
5. 发现旧文档与任务不一致时，核对原始决定和当前代码，再修改；不要仅按最新文件日期判定哪个正确。

### 完成时

1. 将稳定的产品和技术结论合入当前说明，移除该说明中已失效的现行规则。
2. 记录实际修改、验证命令／环境、结果和未验证项；为需要留存的测试结果保留可复查证据。
3. 在项目已有变更入口（`CHANGELOG.md` 或索引的日期章节）增加或更新简短条目，并链接主要说明和任务记录。
4. 新增、改名、替代文档时更新 `INDEX.md` 及受影响链接。
5. 检查代码、原型和文档之间的关键参数及行为是否一致。
6. 需要提交代码时，将相关文档纳入同一提交或 PR 的检查范围。实际提交、推送和发布仍遵循用户授权。

## 6. 修改、版本与历史规则

### 当前说明：原位更新

- 例如内容分段门槛由 3 分钟改为 10 分钟，应直接更新当前产品／技术说明中的门槛、边界和验收约定。
- 更新文档日期，并在变更记录中写清“改了什么、为什么、影响什么”。
- 使用 Git 保存内容历史，不复制为 `design-v2.md`、`design-final.md`。
- 只有确实并存的版本、协议或方案才维护多份，并写清各自适用范围和默认选择。

### 历史证据：保留事实

- 历史实验曾使用 3 分钟门槛，应保留当时的方法与结果；在文首补充“后续已调整，见……”链接。
- 历史测试失败不能被新一轮通过覆盖掉；追加新的验证日期、版本和结论。
- 允许修复错字、断链及明确错误。涉及结论修正时追加勘误，说明修正原因。
- 旧设计被替代时，旧文档标为 `superseded` 并链接新文档；新文档列出取代来源。

### 长期事实：只维护一个主要来源

- 产品行为归产品说明；表结构归数据设计；协议归接口说明；默认阈值归对应技术说明。
- 其他文档通过链接引用。必须引用数值时注明适用版本，变更时一并检查引用处。
- 计划和验证可以记录当次取值，但不再承担全项目当前规则的唯一说明职责。

## 7. 文档元信息与状态

新增长期说明和独立任务记录建议使用轻量元信息。简单变更条目不强制重复这一块。

```yaml
---
id: content-segmentation
type: technical                 # product / technical / plan / verification / decision / release
status: draft                   # draft / current / superseded / archived
updated: 2026-10-31
scope: iPhone 内容分段
related:
  - ../product/recording.md
---
```

- `id` 保持稳定；`updated` 记录内容实际修改日期。
- `current` 表示这是当前采用的说明，不表示所有功能已实现或所有测试通过。
- `superseded` 必须有替代文档链接；`archived` 说明归档原因和适用历史范围。
- 涉及交付时，在正文另列“实现状态”和“验证范围”。例如：代码完成，模拟器已验证，真机待验证，尚未发布。
- 验证记录补充：验证日期、平台／设备、关键配置、提交或构建标识。工作区有未提交修改时明确说明，不仅写一个不对应产物的提交号。
- 批准信息仅在需要时记录实际证据；Agent 不代替用户批准，不推测负责人。

## 8. 日期索引与验证证据

### 变更记录

一个逻辑变更一条简短记录，不把聊天轮次或每次编辑都当作新变更。

```markdown
## 2026-10-31

### Ask AI：发送后清空输入框

- 变化：问题成功写入本机历史后清空；后续回答不修改新草稿。
- 原因：原流程等回答完成后才清空。
- 验证：发送专项测试、模拟器界面；真机尚未验证。
- 关联：产品说明、技术说明、任务验证记录。
```

实际条目使用可点击的相对链接；涉及回滚和数据兼容时补充影响说明。变更日期、验证日期和发布日期分别记录。历史文档无明确日期时填“未标注”，不用文件 mtime 推断。

### 验证证据

- 分开记录静态检查、自动测试、编译、模拟器交互、真机端到端和发布验证。
- “编译成功”不等于“真机功能通过”；设计文档与计划勾选不是验收证据。
- 失败、限制和未验证项保留在结果旁，不能只写“已完成”。
- `/tmp` 可以存临时日志，但长期文档同时保留足够的命令、环境和结果摘要。需要作为审计依据的脱敏附件放稳定位置。
- 不提交 API Key、Token、密码、用户原始录音、未脱敏截图或大体积构建产物。

## 9. 与 Superpowers 和其他 skills 的配合

| Skill／流程 | 应承担的作用 | 项目文档约定 |
| --- | --- | --- |
| `brainstorming` | 澄清需求、讨论方案、形成可评审设计 | 先查已有当前说明；新设计引用它，完成后将采用的结论合入 |
| `writing-plans` | 将已确定的方案拆成实施任务 | 一次任务一份计划；步骤链接设计与验收，不重复整篇产品文档 |
| `executing-plans`／开发流程 | 执行任务并跟踪进展 | 更新原计划，记录偏差和验证结果 |
| `systematic-debugging` | 用证据定位原因 | 根据问题影响，写入现有记录或独立事故记录 |
| `verification-before-completion` | 完成声明必须有验证依据 | 结论与证据、环境、未验证项一同保存 |
| Product Engineering 系列 | 较大项目的产品、研发、测试与发布协作 | 按项目规模选用产物；同一项需求只维护一份主要说明，允许引用已有文档 |

Superpowers 默认的 `docs/superpowers/specs/` 和 `plans/` 可以继续作为现有项目的任务记录目录。新项目可以在明确采纳的项目规则中指定 `docs/work/` 路径；路径约定需要传递给执行 Agent，不能假定 skill 会自动发现。

本规则应通过项目 `AGENTS.md` 明确引用。通用 skill 与已明确的项目／用户约定不一致时，遵循适用的指令优先级，并说明实际采用的约定。使用某个 skill 不意味着要为所有小任务自动生成同样数量的文档。

## 10. 建议加入新项目 AGENTS.md 的执行条款

以下模板供其他新项目采纳时使用；本仓库已通过根目录 `AGENTS.md` 明确采用。

```markdown
## 文档维护

- 文档根目录为 `<project-docs-root>`；开始任务前阅读 INDEX.md 和对应模块说明。
- 遵循 `<project-docs-root>/documentation-rules.md`。
- 新增前先搜索，优先更新既有文档；每个主题维护一个当前说明。
- 文档量随任务风险和复杂度确定，小修复可使用已有记录和变更条目。
- 产品行为、技术规则、数据结构变化时同步更新相关说明与原型。
- 独立任务记录使用 `work/YYYY-MM-DD-topic/`；已有任务继续更新原目录。
- 完成前更新变更与索引，检查链接、关键参数、验证依据和未验证项。
- 保留历史事实；替代关系明确标注，不把计划写成已实现或已发布。
- 不提交凭据、未脱敏用户资料和本机临时产物。
```

使用前将 `<project-docs-root>` 替换为真实路径。现有项目可将任务记录路径替换为已有的 `superpowers` 目录，无需先搬迁所有文件。

## 11. WiseLife 的渐进落地建议

1. 保留现有文档位置与 [总索引](../apps/wrist-notes/docs/INDEX.md)，避免批量移动破坏引用。
2. 先为“产品全貌、录音与同步、内容分段、数据与检索、AI 与隐私”确定当前主要说明文件，逐步补齐缺项。
3. 把新任务稳定结论合入这些说明；已有任务继续在原计划与验证文件更新。
4. 新建简短变更记录，历史日期索引继续作为材料入口；不把索引自动等同为已发布功能清单。
5. 对确实冲突的旧说明补充适用版本和替代链接；历史证据保留。
6. 仓库根目录 `AGENTS.md` 已写明文档路径和维护要求，本仓库后续任务按此执行。其他仓库可在初始化时复用本文和相应执行条款。
